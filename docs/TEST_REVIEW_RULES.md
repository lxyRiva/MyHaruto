# 测试+审查规则

## §1 身份与模式切换

**测试和审查由同一会话承担，通过模式切换。**

开工第一条消息必须显式声明模式：
- **测试模式**：「切换为测试模式」
- **审查模式**：「切换为审查模式」

## §2 测试模式职责

**只做：**
- 按卡内验收清单逐条跑
- 出测试报告（两段制：已实点+证据 / 未完成+清单）

**不做：**
- 不改任何代码
- 不改任何文件
- 发现问题回报规划层，由开发修复

## §3 审查模式职责

**只做：**
- 读代码与 diff（只读）
- 跑 Scope 锁（diff 文件清单 ⊆ 卡内允许清单）
- 跑共享函数唯一性 grep
- 跑搬移审计（diff 零逻辑变更）
- 出审查报告

**不做：**
- 不改代码
- 不改文件

## §4 分级验收（按风险）

| 风险档 | 流程 |
|---|---|
| 高风险（数据层/迁移） | 开发 → 测试 → 审查 → 手测 → commit |
| 中风险（多文件/接口变更） | 开发 → 测试 → 手测 → commit |
| 低风险（单文件小改） | 开发 → 手测 → commit |

## §5 测试轻量化

**只跑：**
1. `git diff --stat` 范围确认
2. 卡内新增验收项
3. 2-3 个回归抽查项

**例外**：数据迁移卡必须跑 `verify:data` + 迁移路径手测。

## §6 审查触发条件

**只在以下情况启动审查：**
- 搬移/迁移类卡
- 接口签名变更
- 数据层变更

**其余卡零审查。**

## §7 报告格式

**两段制：**

**第一段：已实点 + 证据**
- 逐条验收项
- 每条附截图/录屏索引
- 数据级验证（如需要）

**第二段：未完成 + 清单**
- 未做项
- 原因（环境/工具/能力）
- 用户手测步骤
- 通过标准

## §8 证据要求

**禁止纯文字"实点通过"。每条必附：**
- 截图 或 录屏
- 每条附 1 个反例（故意做应失败的操作，证明规则生效）

## §9 禁止行为

1. 测试会话改代码（违反 = 流程事故）
2. 审查会话改文件（违反 = 流程事故）
3. 报告无证据
4. 未切模式就开工
